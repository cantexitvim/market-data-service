# Market Data Service

Market Data Service — это асинхронный REST API для сбора, хранения и получения исторических значений индексов BTC/USD и ETH/USD с использованием публичного API Deribit.

Проект написан на Python с использованием FastAPI, SQLAlchemy, PostgreSQL и Celery. Сбор цен выполняется периодически в фоновой задаче, а сохранённые данные доступны через HTTP API с поддержкой фильтрации по датам, сортировки и пагинации.

## Что умеет проект

- получение индексов BTC/USD и ETH/USD из публичного API Deribit;
- автоматический сбор цен каждую минуту;
- сохранение истории цен в PostgreSQL;
- получение исторических значений с фильтрацией по диапазону дат;
- сортировка результатов по времени;
- пагинация с помощью `limit` и `offset`;
- получение последнего сохранённого значения цены для выбранного индекса;
- асинхронное взаимодействие с внешним API и базой данных;
- управление схемой базы данных через Alembic;
- выполнение фоновых задач через Celery;
- периодический запуск задач через Celery Beat;
- логирование ошибок приложения и фоновых задач;
- автоматические проверки кода и тестов через GitHub Actions.

## Архитектура проекта

Приложение разделено на несколько слоёв, каждый из которых отвечает за свою часть работы.

```text
app/
├── api/
│   └── v1/                 # HTTP-эндпоинты API
├── clients/                # Клиенты внешних API
├── core/                   # Настройки, логирование и ошибки
├── database/
│   ├── repositories/       # Запросы к базе данных
│   ├── models.py           # SQLAlchemy-модели
│   ├── session.py          # Подключение и сессии БД
│   └── uow.py              # Unit of Work
├── schemas/                # Pydantic-схемы
├── services/               # Бизнес-логика
├── tasks/                  # Фоновые задачи Celery
├── celery_app.py           # Конфигурация Celery и расписания
├── main.py                 # Создание FastAPI-приложения
├── middleware.py           # Middleware для логирования ошибок
└── redis.py                # Управление подключением к Redis

alembic/                    # Миграции базы данных
tests/                      # Тесты
Dockerfile
docker-compose.yml
pyproject.toml
poetry.lock
```

API-слой отвечает за обработку HTTP-запросов и валидацию параметров. Сервисный слой содержит бизнес-логику, а репозиторий инкапсулирует запросы к PostgreSQL.

Для управления сессией и транзакцией используется Unit of Work. Он предоставляет сервисному слою доступ к репозиториям и выполняет commit или rollback в зависимости от результата операции.

## Как работает сбор данных

Сбор цен выполняется в фоновой задаче Celery, расписание которой задаётся через Celery Beat.

Каждую минуту задача:

1. Создаёт HTTP-сессию для работы с Deribit.
2. Запрашивает индекс BTC/USD.
3. Запрашивает индекс ETH/USD.
4. Сохраняет полученные значения в PostgreSQL вместе с тикером и временем получения.

Цены запрашиваются через публичный эндпоинт Deribit `public/get_index_price`.

Для взаимодействия с внешним API используется `aiohttp`. Полученные значения обрабатываются с использованием `Decimal`, чтобы не переводить цены в двоичный тип `float` при разборе JSON.

## Работа с данными

В PostgreSQL хранится история полученных значений. Каждая запись содержит:

- `id` — идентификатор записи;
- `ticker` — тикер индекса (`btc_usd` или `eth_usd`);
- `price` — значение индекса;
- `timestamp` — время получения значения в формате Unix timestamp, в секундах.

Для хранения цены используется тип `NUMERIC(20, 8)`, а для временной метки — `BIGINT`.

На пару полей `ticker` и `timestamp` создан индекс, который помогает выполнять запросы по конкретному индексу и времени.

Исторические значения не перезаписываются при каждом новом запросе: новые результаты сбора добавляются в таблицу `prices`.

## API

Базовый префикс API:

```text
/api/v1
```

### Получение истории цен

```http
GET /api/v1/prices
```

Параметры запроса:

| Параметр | Тип | Описание |
|---|---|---|
| `ticker` | `btc_usd` или `eth_usd` | Обязательный тикер индекса |
| `from_date` | `YYYY-MM-DD` | Начальная дата диапазона |
| `to_date` | `YYYY-MM-DD` | Конечная дата диапазона |
| `sort_desc` | `bool` | Сортировка по времени в обратном порядке |
| `limit` | `int` | Количество записей, от 1 до 100, по умолчанию 10 |
| `offset` | `int` | Смещение выборки, по умолчанию 0 |

Пример:

```http
GET /api/v1/prices?ticker=btc_usd&from_date=2026-10-01&to_date=2026-10-10&sort_desc=true&limit=20&offset=0
```

Ответ содержит список записей, общее количество результатов и параметры пагинации:

```json
{
  "data": {
    "items": [
      {
        "id": 1,
        "ticker": "btc_usd",
        "timestamp": 1790899200,
        "price": "67450.25000000"
      }
    ],
    "total": 1,
    "limit": 20,
    "offset": 0
  }
}
```

Значения в примере приведены для иллюстрации формата ответа.

### Получение последней цены

```http
GET /api/v1/prices/last?ticker=btc_usd
```

Возвращает последнюю сохранённую запись для выбранного индекса.

Пример ответа:

```json
{
  "data": {
    "id": 1,
    "ticker": "btc_usd",
    "timestamp": 1790899200,
    "price": "67450.25000000"
  }
}
```

## Design Decisions

### Разделение ответственности

HTTP-обработка, бизнес-логика и доступ к данным вынесены в отдельные слои. Это позволяет тестировать сервисную логику независимо от HTTP-обработчиков и изолировать SQL-запросы в репозитории.

### Асинхронный ввод-вывод

FastAPI, асинхронный SQLAlchemy и `aiohttp` используются для операций ввода-вывода. При ожидании ответа от внешнего API или PostgreSQL приложение может обслуживать другие операции, не блокируя event loop на время ожидания.

### Отдельный процесс для фоновых задач

Сбор цен вынесен в Celery, а расписание управляется через Celery Beat. Благодаря этому периодический сбор не привязан к обработке HTTP-запросов и выполняется независимо от обращений к API.

Redis используется как брокер сообщений Celery. Он связывает планировщик и обработчик фоновых задач, позволяя им работать в отдельных процессах и контейнерах.

### Decimal для финансовых значений

При обработке ответа Deribit JSON разбирается с использованием `Decimal` для чисел с плавающей точкой. В сочетании с типом `NUMERIC` в PostgreSQL это позволяет избежать лишних потерь точности, связанных с двоичным представлением `float`.

### Индекс по тикеру и времени

Основные запросы к истории ограничиваются конкретным тикером и могут фильтроваться по времени. Поэтому создан индекс по полям `ticker` и `timestamp`, соответствующий характеру этих запросов.

### Unit of Work для транзакций

Сервисный слой работает с репозиторием через Unit of Work. Завершение операции приводит к commit, а исключение — к rollback. Это централизует управление транзакциями и не требует размещать одинаковую логику управления сессией в каждом методе сервиса.

### Контейнеризация окружения

Docker Compose используется для запуска PostgreSQL, Redis, API, Celery Worker и Celery Beat. Внутри Docker-сети компоненты обращаются друг к другу по именам сервисов, что позволяет не привязывать конфигурацию контейнеров к адресам конкретной машины.

## Запуск через Docker Compose

Для запуска необходимы Docker и Docker Compose.

Сначала нужно создать .env файл:

```
cp .env.example .env
```

Затем выполнить:

```bash
docker compose up --build
```

При запуске контейнер `web` применит миграции Alembic и запустит FastAPI. Celery Worker будет обрабатывать фоновые задачи, а Celery Beat — запускать сбор цен по расписанию.

API будет доступен по адресу:

```text
http://localhost:8000
```

Если `SHOW_DOCS=True`, интерактивная документация будет доступна по адресам:

```text
http://localhost:8000/docs
http://localhost:8000/redoc
```

## Локальный запуск без контейнера приложения

Для локального запуска Python-приложения PostgreSQL и Redis должны быть запущены и доступны по адресам, указанным в `.env`.

Создать .env файл:

```
cp .env.example .env
```

Установить зависимости:

```bash
poetry install
```

Применить миграции:

```bash
poetry run alembic upgrade head
```

Запустить API:

```bash
poetry run uvicorn app.main:app --reload
```

В отдельных терминалах запустить Celery Worker и Celery Beat:

```bash
poetry run celery -A app.celery_app:celery_app worker --loglevel=INFO
```

```bash
poetry run celery -A app.celery_app:celery_app beat --loglevel=INFO
```

## Миграции

Для версионирования схемы базы данных используется Alembic.

Применить миграции:

```bash
poetry run alembic upgrade head
```

Создать новую миграцию на основе изменений моделей:

```bash
poetry run alembic revision --autogenerate -m "describe changes"
```

## Тесты и качество кода

Для тестирования используется Pytest с поддержкой асинхронных тестов через pytest-asyncio. В тестах внешние зависимости можно заменять моками, чтобы проверять поведение сервисов и клиентов независимо от реальных сетевых запросов.

Запуск тестов:

```bash
poetry run pytest
```

Проверка кода через Ruff:

```bash
poetry run ruff check .
```

Проверки ruff автоматически запускаются pre-commit при создании нового коммита.
